# Лабораторна робота №1
## Основи Java та модифікатори доступу

### 🎯 Мета роботи

Розібратися, як працюють модифікатори доступу, наслідування та контракти `equals`/`hashCode` в Java — через **аналіз, виправлення і тестування** коду предметної області **«Деканат університету»**.

> **Про AI.** Використовувати AI-асистенти (ChatGPT, Claude, Copilot тощо) **дозволено** на всіх етапах. Оцінюється не те, чи писали ви код руками, а те, чи розумієте ви його — це перевіряється тестами, протоколом роботи з AI та усним захистом. Код, який ви не можете пояснити, не зараховується, навіть якщо він працює.

### 📦 Специфікація предметної області

Пакети: `ua.university.model`, `ua.university.util`.

#### `Person` (абстрактний)
- Поля `protected`: `firstName`, `lastName`, `email`
- Конструктор `protected` — клас не інстанціюється напряму
- Імʼя/прізвище: кирилиця або латиниця, апостроф, дефіс; 2–50 символів; нормалізуються до вигляду «Іван» (перша велика, решта малі; дефісні прізвища — «Нечуй-Левицький»)
- Email: нормалізується до нижнього регістру, валідується
- `getFullName()`, `equals`/`hashCode` (через `getClass()`), `toString()` через шаблонний метод `protected fieldsString()`

#### `Student extends Person`
- Поля `private`: `studentId`, `group`
- `studentId`: 2 великі латинські літери + 8 цифр (`ST00012345`); коротка числова частина доповнюється нулями (`st42` → `ST00000042`)
- Конструктор `private`; створення тільки через фабрики:
  - `register(firstName, lastName, studentId, group)` — email **генерується** з імені
  - `load(firstName, lastName, email, studentId, group)` — email береться як збережений

#### `Teacher extends Person`
- Поля `private`: `department`, `position` (непорожні рядки)
- Фабрики `register`/`load` — аналогічно Student

#### `Group`
- Поля `private`: `int number`, `String specialty`, `int startYear`
- `number`: 1..20; `specialty`: код з 2–4 великих кириличних літер («КН», «ІПЗ»), нормалізується до верхнього регістру
- **Повний номер групи не зберігається — обчислюється**: `<specialty><number>-<XX>`, де `XX` — дві останні цифри року (`КН1-21`). Формат живе в `GroupUtils.formatGroupFullNumber(Group)`; `Group.getFullNumber()` делегує туди ж
- Рік вступу — **два різні правила**:
  1. *Інваріант даних* (завжди, у конструкторі): `1901 <= startYear <= поточний рік`
  2. *Бізнес-правило реєстрації* (тільки в `register`): нова група не старша за 6 років
- `register(...)` — інваріант + бізнес-правило; `load(...)` — тільки інваріант. Група 2015 року має завантажуватися, але не реєструватися
- Дві групи рівні, якщо збігаються всі три поля (номери груп перевикористовуються між роками)

#### `Subject`
- Поля `private`: `title` (непорожній), `credits` (1..20 кредитів ЄКТС)
- Фабрика `of` (правила створення і відновлення не різняться — окремі `register`/`load` не потрібні)

#### `Course`
- Поля `private`: `subject`, `teacher`, `group` — усі not-null
- Фабрика `of`

#### Пакет `ua.university.util`
- `ValidationHelper` — **package-private**, private конструктор. Методи: `isStringMatchPattern`, `isNumberBetween`, `isStringLengthBetween`
- `PersonUtils`, `StudentUtils`, `GroupUtils` — **public**, private конструктори; внутрішньо використовують `ValidationHelper`
- Константи правил (діапазони, патерни) — package-private, поруч зі своїми перевірками

#### Загальні вимоги
- Валідація у конструкторах **і** сеттерах; сеттери `final` (конструктор не має викликати перевизначуваний метод)
- Повідомлення про помилку описує, **що очікується**, і показує отримане значення: `"Group number must be between 1 and 20, got: 99"`
- `equals`/`hashCode` — разом, з дотриманням контракту; у нащадків — через `super`

### 📋 Завдання

#### Частина 1. Знайди, поясни, виправ, доведи (30%)

Ви отримуєте **персональний варіант** проєкту (тека `variant-NN`), у якому реалізація навмисно відхиляється від специфікації у **8 місцях**. Помилки стосуються тем лаби: модифікатори доступу, `super()`, контракт `equals`/`hashCode`, валідація, наслідування.

Здати:
1. Список знайдених відхилень: *де* (клас, метод) і **чому це проблема** — не «так не прийнято», а *що саме і за якого сценарію зламається*
2. Виправлений код, що відповідає специфікації
3. **По одній перевірці на кожну знайдену помилку** (25%) — у класі `ChecksMain` (див. «Формат перевірок» нижче): перевірка дає `FAIL` на коді варіанта і `OK` на виправленому

#### Частина 2. Генерація email з транслітерацією (25%)

`PersonUtils.generateEmailFromName(firstName, lastName)` → `<translit(first)>.<translit(last)>@university.edu.ua`.

Транслітерація — за **постановою КМУ №55 від 27.01.2010**:
- позиційні правила для є, ї, й, ю, я (початок слова vs всередині)
- «зг» → `zgh`
- мʼякий знак та апостроф (усі варіанти: `'`, `’`, `ʼ`) не передаються
- після дефіса діють правила початку слова

Ви отримуєте **персональний набір прізвищ** — ваша реалізація має правильно транслітерувати кожне. Мінімум 6 власних перевірок на граничні випадки (теж у `ChecksMain`). *Підказка: AI генерує транслітерацію «майже правильно» — розбіжності шукаються тестами проти тексту постанови.*

#### Формат перевірок (замість юніт-тестів)

Бібліотеки тестування ми ще не проходили, тому перевірки пишуться простим класом `ChecksMain`:

```java
public class ChecksMain {
    static void check(String what, boolean ok) {
        System.out.println((ok ? "OK   " : "FAIL ") + what);
    }

    public static void main(String[] args) {
        Group a = Group.load(1, "КН", 2021);
        Group b = Group.load(1, "КН", 2021);
        check("equal groups are equal", a.equals(b));
        check("equal groups have equal hash codes", a.hashCode() == b.hashCode());

        // перевірка "невалідне значення відхиляється":
        boolean thrown;
        try {
            Subject.of("Yoga", 99);
            thrown = false;
        } catch (IllegalArgumentException e) {
            thrown = true;
        }
        check("invalid credits are rejected", thrown);
    }
}
```

Достатньо мови, яку ви вже знаєте: виклики методів, порівняння, try/catch. Жодних бібліотек чи колекцій.

Вимоги: на **виправленому** коді всі рядки — `OK`; для кожної перевірки ви маєте вміти показати, що на коді **варіанта** вона давала `FAIL` (це питання захисту). Для помилок, які не проявляються в поведінці (наприклад, неправильний модифікатор), замість перевірки достатньо пояснення у списку відхилень.

#### Частина 3. Рефлексія щодо AI (обовʼязкова, без неї робота не приймається)

Пів сторінки, один із двох форматів — на ваш вибір, оцінюються однаково:

**Якщо використовували AI при виконанні** — протокол:
- якими інструментами і промптами користувалися (ключові — дослівно)
- **що AI зробив неправильно чи неоптимально** і як ви це виявили
- що виправили самостійно і чому

**Якщо не використовували** — аналіз: згодуйте AI-асистенту **одне** будь-яке своє виправлення або одну свою перевірку і попросіть його оцінити/покращити. Опишіть: з чим у його відповіді погоджуєтеся, з чим ні, і чому.

«AI все зробив ідеально» — валідна відповідь тільки разом з описом того, *як саме ви перевіряли*.

#### Частина 4. Захист (20%)

5 хвилин, 3–4 питання **по вашому коду**. Орієнтовний рівень:
- Чому `email` у `Person` — `protected`? Що зміниться при `private`?
- Приберіть `hashCode()` — яка ваша перевірка дасть FAIL і чому? Де ця помилка вистрелила б у реальній програмі?
- Чому конструктор `Person` — `protected`, а `Student` — `private`?
- Чому `fieldsString()` можна перевизначати, а `setEmail()` — `final`?
- Що станеться 1 січня з валідацією року вступу? Чому правило «−6 років» не в конструкторі?
- `Person` абстрактний без жодного абстрактного методу — це нормально?
