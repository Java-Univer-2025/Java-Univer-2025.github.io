# Лабораторна робота №6
## Файли, серіалізація та валідація

**Максимальна оцінка — 20 балів.**

### 🎯 Що ви навчитеся робити

Зберігати вміст репозиторіїв у файлах і відновлювати його назад — у JSON і YAML, без ручного розбору рядків, як у ЛР3. Описувати правила для даних анотаціями, а не `if`-ами в конструкторах, і писати власне правило, коли стандартних не вистачає. Завантажувати дані так, як це роблять реальні системи: один битий запис не валить усе завантаження, а відкидається з поясненням.

### 📋 Що зробити

#### Частина 1. Файли

**1. Файли даних.** У каталозі `data/` в корені репозиторію — по файлу для кожної з двох сутностей із ЛР5: одна в JSON, друга в YAML. У кожному файлі щонайменше 15 записів, серед них:

- щонайменше три невалідні — кожен порушує інше правило з частини 2;
- щонайменше один дублікат ідентичності.

Окремо — файл `data/broken.json` із синтаксичною помилкою.

Файли пишете самі, а не генеруєте програмою.

**2. Узагальнений клас для файлів.** Створіть `FileStorage<T>`:

```java
public class FileStorage<T> {
    public FileStorage(Class<T> type) { ... }

    public List<T> load(Path file) throws IOException
    public void save(Path file, List<T> items) throws IOException
}
```

Формат визначаєте за розширенням файлу (`.json`, `.yaml`, `.yml`) через enum `DataFormat`. Невідоме розширення — виключення. Один `FileStorage` працює з обома форматами; окремих класів під JSON і YAML немає.

Дати у файлах — рядками ISO (`2026-11-02`), а не масивами чисел.

**3. Конфігурація через `Properties`.** Файл `app.properties` у `src/main/resources` містить шляхи до файлів даних. `Main` бере шляхи звідти — жодних шляхів у коді.

Якщо потрібного ключа немає, програма кидає виключення, в тексті якого є назва ключа.

#### Частина 2. Валідація

**4. Стандартні анотації.** На полях обох сутностей — щонайменше п'ять різних анотацій Jakarta Validation: `@NotNull`, `@NotBlank`, `@Size`, `@Positive`, `@Min`, `@Max`, `@Email`, `@Pattern`, `@Past`, `@FutureOrPresent` тощо. Кожна — з власним повідомленням українською.

Ручні перевірки з ЛР1 (`IllegalArgumentException` у конструкторах), які дублюють анотації, приберіть. Що лишити в конструкторі, а що віддати валідатору — ваше рішення. Поясніть його в `README.md` гілки `lab6` двома-трьома реченнями, з урахуванням того, як Jackson створює об'єкти з файлу.

**5. Власна анотація.** Створіть анотацію-обмеження з власним `ConstraintValidator` для правила свого домену, яке не виражається стандартними анотаціями.

Правило має бути перехресним — перевіряти два поля одного об'єкта: дата завершення пізніше дати початку, знижка не більша за ціну тощо. Тому анотація ставиться на клас або record, а не на поле.

#### Частина 3. Завантаження з відбраковкою

**6. Завантажувач.** Клас `DataLoader` читає файл через `FileStorage`, проганяє кожен об'єкт через `Validator`, валідні додає в репозиторій і повертає результат завантаження — record `LoadResult`: скільки записів прочитано, скільки додано і список відкинутих. Відкинутими вважаються:

- запис, що порушує правила валідації: його номер у файлі, поле й повідомлення — усі порушення, а не лише перше;
- дублікат ідентичності;
- файл, який не вдалося прочитати: синтаксична помилка або файлу немає. Завантаження інших файлів при цьому триває.

Жоден із файлів у `data/` не валить програму.

**7. Логування через SLF4J** — ті самі три рівні, що й раніше. На кожен файл: скільки записів прочитано, скільки додано, скільки відкинуто. На кожен відкинутий запис — окремий рядок. Файл, який не вдалося прочитати, — найвищим із ваших рівнів.

**8. Тести на JUnit 5, щонайменше десять.** Файли в тестах створюєте в `@TempDir`, а не в `data/`.

- JSON: `save`, потім `load` дає рівний список;
- те саме для YAML;
- дата у збереженому файлі записана рядком ISO;
- невідоме розширення файлу кидає виключення;
- кожна стандартна анотація ловить невалідне значення: `validator.validate` повертає порушення з очікуваним полем (можна одним параметризованим тестом);
- власна анотація: валідний об'єкт проходить, невалідний — ні;
- завантаження файлу з невалідними записами: у репозиторії тільки валідні, у `LoadResult` — очікувана кількість відкинутих;
- дублікат потрапляє у відкинуті, а не вилітає виключенням назовні;
- синтаксично битий і неіснуючий файл не валять завантаження;
- відсутній ключ у `Properties` дає виключення з назвою ключа.

**9. Оновіть `Main`.** Показати треба:

1. читання конфігурації;
2. завантаження обох файлів із підсумком: скільки прочитано, додано, відкинуто;
3. вивід відкинутих записів — по рядку на кожен;
4. спробу завантажити `broken.json`;
5. зміну вмісту репозиторію й збереження в новий файл;
6. повторне завантаження збереженого файлу — вміст збігається;
7. логування.

### ✍️ Оформлення

Коментарі, javadoc, `@DisplayName` і тексти виключень — англійською. Українською — тільки те, що бачить користувач: рядки виводу в `Main` і повідомлення анотацій валідації.

Raw types заборонені. Шляхів до файлів у коді немає — тільки в `app.properties` і в тестах через `@TempDir`.
