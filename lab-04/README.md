### 📋 Що зробити

**1. Функціональний інтерфейс `IdentityExtractor<T>`** — як витягти з обʼєкта його унікальне поле:

```java
@FunctionalInterface
public interface IdentityExtractor<T> {
    String identityOf(T item);
}
```

Реалізації передаєте лямбдами — окремих класів під це не пишете.

**2. Клас `GenericRepository<T>`** з таким мінімумом:

```java
public GenericRepository(String name, IdentityExtractor<T> extractor)

public void            add(T item)
public boolean         addIfAbsent(T item)
public boolean         removeByIdentity(String identity)
public Optional<T>     findByIdentity(String identity)
public List<T>         findAll()
public int             size()
```

Всередині зберігаєте елементи в `Map<String, T>`, де ключ — identity. Яку саме реалізацію `Map` взяли — ваш вибір, на захисті поясните.

- `add(null)` і елемент із порожньою identity → `IllegalArgumentException`;
- `findByIdentity` повертає `Optional<T>`, а не `null`;
- `findAll()` повертає такий список, яким зовнішній код не може зіпсувати стан репозиторію.

**3. Контракт дублікатів.** `add` з identity, яка вже є, кидає власне **unchecked** `DuplicateIdentityException` (наслідує `IllegalStateException`); у повідомленні — identity й назва репозиторію. `addIfAbsent` на тому самому обʼєкті нічого не кидає й повертає `false`.

Унікальність забезпечує репозиторій, а не сутність: конструктори та компактні конструктори з ЛР1–ЛР2 про дублікати нічого не знають і не дізнаються.

**4. Два узагальнені методи з wildcard:**

```java
public void addAll(Collection<? extends T> items)

public static <E> Set<String> duplicateIdentities(
        Collection<? extends E> items, IdentityExtractor<E> extractor)
```

`duplicateIdentities` повертає ті identity, що у вхідній колекції трапляються більш ніж один раз, і живе в утилітному класі — у репозиторій він не складається.

**5. Перевірте репозиторій на трьох різних типах** вашого домену — щонайменше один record і щонайменше один ✎-клас зі змінюваними полями. Для кожного типу — свій екземпляр репозиторію і своя лямбда-`IdentityExtractor`.

Для ✎-класу беріть identity з поля, яке після додавання не змінюється. Чому — питання на захист.

**6. Наповніть один репозиторій із CSV-файла ЛР3.** Додайте у файл щонайменше один рядок із уже наявною identity, щоб шлях із дублікатом спрацьовував на справжніх даних, а не лише в `Main`.

**7. Логування через SLF4J** — ті самі три рівні, що й у ЛР3: `INFO` на успішні операції, `WARN` на відхилений дублікат і ненайдений елемент, `ERROR` там, де виключення не ковтається, а летить далі. Одну й ту саму подію логуйте в одному місці: або в репозиторії, або у викликача, але не двічі.

**8. Тести на JUnit 5, щонайменше вісім:**

- `add` + `findByIdentity` знаходить доданий елемент;
- `findByIdentity` на відсутній identity повертає порожній `Optional`;
- повторний `add` кидає `DuplicateIdentityException`;
- `addIfAbsent` повертає `false` і не змінює `size()`;
- `removeByIdentity` на наявному й на відсутньому елементі;
- спроба змінити результат `findAll()` не змінює репозиторій;
- той самий клас репозиторію працює щонайменше з двома різними типами;
- `duplicateIdentities` знаходить саме ті identity, що повторюються.

Тести не повинні залежати від файла в `data/`.

**9. Оновіть `Main`.** Показати треба:

1. три репозиторії різних типів і пошук за identity — знайдено і не знайдено;
2. наповнення репозиторію з CSV-файла;
3. додавання дубліката через `add` (із перехопленням) і через `addIfAbsent` — різницю видно у виводі;
4. видалення наявного й відсутнього елемента;
5. список дублікатів у вхідних даних;
6. логування всіх трьох рівнів.

**10. Порівняйте пошук у `Map` і в `List`.** Окремий клас, репозиторій не змінюється.

Згенеруйте 100 000 обʼєктів одного типу й покладіть їх у репозиторій. Список для лінійного пошуку візьміть із `findAll()` **один раз, до вимірювань** — усередині циклу ви міряли б копіювання, а не пошук.

Лінійний пошук пишете самі, з тим самим `IdentityExtractor`:

```java
static <E> Optional<E> linearSearch(
        List<E> items, String identity, IdentityExtractor<E> extractor) {
    for (E item : items) {
        if (identity.equals(extractor.identityOf(item))) {
            return Optional.of(item);
        }
    }
    return Optional.empty();
}
```

Три сценарії пошуку — перший елемент, останній, відсутній — обидвома способами. Перед замірами зробіть прогін на прогрів, кожен замір повторіть кілька разів і беріть медіану або мінімум, а не перше число.

Результат — таблицею в `README.md` гілки `lab4` плюс два-три речення висновку: де різниця величезна, де її майже немає і чому.

### ✍️ Оформлення

Коментарі, javadoc, `@DisplayName` і тексти виключень — англійською. Українською — тільки те, що бачить користувач: рядки виводу в `Main`.

Raw types заборонені: `GenericRepository repo = new GenericRepository(...)` без параметра типу — помилка, а не стиль. `Object` як універсальний тип і приведення через `(T)` — теж.

### 🎤 Захист

5 хвилин, 3–4 питання по **вашому** коду й по діффу у вашому PR. Орієнтовно:

- Чому `IdentityExtractor<T>` — окремий інтерфейс, а не спільний інтерфейс `Identifiable`, який реалізують усі ваші сутності? Що довелося б змінити в record-ах?
- Що робить `@FunctionalInterface` і що зміниться, якщо її прибрати?
- Яку реалізацію `Map` ви взяли і що зміниться, якщо замінити її на іншу? А якщо замість `Map` узяти `List`?
- Чому `DuplicateIdentityException` unchecked, а `InvalidDataException` з ЛР3 — checked?
- Що повертає ваш `findAll()` — копію чи саму колекцію? Що станеться, якщо викликач зробить `.clear()` на результаті?
- Чому `addAll(Collection<? extends T>)`, а не `Collection<T>`? Наведіть виклик, який без wildcard не скомпілюється.
- Чому `findByIdentity` повертає `Optional<T>`, а не `null`?
- Що станеться з пошуком, якщо у ✎-класі змінити поле, з якого береться identity, уже після `add`?
- Чи може один екземпляр вашого репозиторію зберігати обʼєкти двох різних типів? Що саме про тип `T` відомо на етапі виконання?
- У якому зі сценаріїв `List` виявився не гіршим за `Map` і чому саме в ньому?
